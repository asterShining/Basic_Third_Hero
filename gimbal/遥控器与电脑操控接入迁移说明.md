# 遥控器与电脑操控接入迁移说明

## 1. 目的

本文档用于把旧工程 `/home/aster/robo-misc/RMUC_HERO/RMUC HERO/code(加自瞄,加ui)mit` 中的“遥控器 + 电脑/自瞄”控制链路，整理后迁移到 `/home/aster/robomaster/Basic_Third_Hero/gimbal`。

本文不是简单描述旧工程做了什么，而是回答下面两个问题：

1. 旧工程的控制链路到底是怎么接起来的。
2. 在 `Basic_Third_Hero` 框架下，应该把这些逻辑写到哪里，哪些地方可以复用，哪些地方不能照搬。

---

## 2. 旧工程的真实链路

### 2.1 遥控器输入链路

旧工程的遥控器输入入口是 `USART3`：

- 串口参数：`100000 baud + even parity`
- 接收方式：`DMA + IDLE`
- 原始帧长：`18 byte`

对应文件：

- `application/remote_control.c`
- `application/remote_control.h`
- `bsp/boards/bsp_rc.c`
- `Src/usart.c`

解析结果包含：

- `rc.ch[0..4]`：5 路通道
- `rc.s[0..1]`：左右拨杆开关
- `mouse.x/y/z`
- `mouse.press_l/press_r`
- `key.v`

这说明旧工程里的“电脑键鼠控制”并不是电脑直接连主控，而是键鼠数据已经通过图传/遥控链路并入了 DBUS 帧，然后由主控统一解析。

### 2.2 电脑输入链路

旧工程的电脑/自瞄输入入口不是 USB，而是 `USART1`：

- `USART1 RX`：主控接收电脑发来的 12 字节数据
- 数据结构：`float x + float y + float distance`
- 接收方式：`DMA + IDLE`

对应文件：

- `MDK-ARM/AutoGimbal.h`
- `MDK-ARM/AutoGimbal.c`

旧协议本质是“原始 float 内存直拷贝”，没有帧头、没有 CRC、没有版本字段、没有长度字段。该协议只适合同一套上位机和同一类 MCU 小端环境，不适合扩展。

### 2.3 电脑输出链路

旧工程在收到 `USART3` 遥控帧后，还会把原始 SBUS 再封一层发到 `USART1 TX`：

- 包格式：`0xA6 + 18B sbus + sum`

对应文件：

- `application/remote_control.c` 中的 `sbus_to_usart1()`

这说明旧工程的 `USART1` 同时承担了两件事：

1. 主控把遥控原始帧转发给电脑。
2. 电脑把自瞄偏差发回主控。

### 2.4 USB 在旧工程中的角色

旧工程虽然启用了 USB CDC，但它只做状态打印，不做控制输入。

对应文件：

- `application/usb_task.c`
- `Src/usbd_cdc_if.c`

因此，旧工程里：

- `USB` = 调试口
- `USART1` = 电脑/自瞄通信口
- `USART3` = 遥控器口

### 2.5 旧工程控制逻辑的分布方式

旧工程的输入消费是分散的，不是统一收口的：

- 底盘直接读 `get_remote_control_point()`
- 云台直接读 `get_remote_control_point()` 和 `get_AUTO_control_point()`
- 射击直接读 `mouse.press_l`、拨杆和按键
- 舵机任务直接读 `ch4`、鼠标右键

对应文件：

- `application/chassis_task.c`
- `application/gimbal_behaviour.c`
- `application/shoot.c`
- `application/servo_task.c`

这类写法能跑，但问题是：

1. 控制源分散，后续加新控制源很难收敛。
2. `USART1` 同时跑“遥控回传”和“自瞄命令”，协议边界弱。
3. 自瞄逻辑耦合在云台行为层，不利于迁移。

## 3. `Basic_Third_Hero` 的正确分层

`Basic_Third_Hero` 已经把输入链路拆成了 3 层：

### 3.1 `modules/remote`

职责：

- 专门解析 `USART3` 上的遥控器数据
- 维护遥控器在线状态
- 提供统一的 `RC_ctrl_t`

对应文件：

- `modules/remote/remote_control.c`
- `modules/remote/remote_control.h`
- `modules/remote/remote.md`

### 3.2 `modules/master_machine`

职责：

- 专门处理视觉/上位机通信
- 支持 `VCP / UART / CAN`
- 统一输出 `Vision_Recv_s`
- 统一发送 `Vision_Send_s`

对应文件：

- `modules/master_machine/master_process.c`
- `modules/master_machine/master_process.h`
- `modules/master_machine/master_process.md`
- `modules/master_machine/sp_vision_protocol.h`

### 3.3 `application/cmd/robot_cmd`

职责：

- 汇总遥控器、键鼠、视觉、反馈信息
- 做模式切换、急停、限幅、控制映射
- 向 `gimbal / shoot / chassis` 发布具体控制量

对应文件：

- `application/cmd/robot_cmd.c`
- `application/cmd/robot_cmd.h`
- `application/cmd/robot_cmd.md`

### 3.4 这一层次关系的核心原则

在这个框架里：

- `remote` 只负责“把遥控器读出来”
- `master_process` 只负责“把上位机读出来/发回去”
- `robot_cmd` 才负责“决定当前到底听谁”
- `gimbal/shoot/chassis` 只负责执行控制量，不再自行读遥控器和上位机

这和旧工程最大的不同是：

旧工程是“输入直接进执行模块”，新框架是“输入先进入 cmd，再由 cmd 下发”。

## 4. 迁移时应该如何写入

## 4.1 遥控器部分

### 应该写到哪里

沿用现成的 `modules/remote/remote_control.c`，不要把旧工程的 `application/remote_control.c` 原样搬过来。

### 原因

因为 `Basic_Third_Hero` 已经完成了这些工作：

- SBUS/DBUS 解包
- 键鼠按键统计
- 遥控在线守护
- `USARTRegister()` 封装

### 正确接法

在 `RobotCMDInit()` 里初始化：

```c
rc_data = RemoteControlInit(&huart3);
```

这一点在现有 `application/cmd/robot_cmd.c` 里已经写好。

### 迁移重点

旧工程里的控制映射不要继续分散写在 `gimbal_task.c`、`shoot.c`、`servo_task.c` 里，而是要集中并到：

- `RemoteControlSet()`
- `MouseKeySet()`

即：

- 拨杆/摇杆含义写进 `robot_cmd.c`
- 发射模式切换写进 `robot_cmd.c`
- 云台/底盘模式切换写进 `robot_cmd.c`

---

## 4.2 电脑/视觉部分

这里分两种方案。

## 5. 推荐方案：放弃旧 `USART1 12字节裸包`，改用 `master_process`

这是推荐方案，也是最符合 `Basic_Third_Hero` 架构的方案。

### 5.1 原因

旧工程的 `12 byte float x/y/distance` 协议有 4 个问题：

1. 没有帧头，丢字节后无法重同步。
2. 没有 CRC，串口毛刺后无法自检。
3. 只适配“小端 + float32”，协议可移植性差。
4. 无法和旧工程的 `USART1 TX sbus回传` 长期共用一条链路。

而 `Basic_Third_Hero` 的 `master_process` 已经支持：

- `USB VCP`
- `UART`
- `CAN`
- `SP` 帧头 + `CRC16`
- 在线守护

### 5.2 建议使用哪种模式

优先级建议如下：

1. `VISION_USE_VCP`
2. `VISION_USE_UART`

如果上位机就在云台板 USB 口上，优先用 `VCP`。
如果上位机必须走 TTL 串口，才用 `UART`。

### 5.3 如何启用

在 `application/robot_def.h` 选择一种：

```c
#define VISION_USE_VCP
// #define VISION_USE_UART
```

### 5.4 初始化写法

在 `application/cmd/robot_cmd.c` 中启用：

```c
vision_recv_data = VisionInit(NULL);      // VCP 模式
vision_recv_data = VisionInit(&huart1);   // UART 模式
```

当前工程里这行被注释了，需要打开。

### 5.5 控制应该写在哪里

上位机接收到的数据先进入：

- `Vision_Recv_s`

然后由 `robot_cmd.c` 决定是否让视觉接管云台：

- `AutoGimbalRun()`
- `RemoteControlSet()`

即：

1. `master_process` 负责解包
2. `robot_cmd` 负责做控制权仲裁
3. `auto_gimbal.c` 负责把视觉目标转换为云台目标角

### 5.6 发送回上位机的数据

`Basic_Third_Hero` 的发送链路已经分好了：

- `VisionSetQuaternion()`
- `VisionSetAltitude()`
- `VisionSetStatus()`
- `VisionSend()`

其中 `VisionSend()` 已经在 `application/robot_task.h` 的 `StartINSTASK()` 里以 1kHz 调用。

所以如果你采用推荐方案，不要再恢复旧工程里的：

- `sbus_to_usart1()`
- `0xA6 + sbus + checksum`

否则会直接污染 `master_process` 的 `USART1`/`USB VCP` 协议流。

### 5.7 推荐方案的迁移结论

如果上位机可以改，那么应该做的不是把旧 `AutoGimbal.c` 原样搬进来，而是：

1. 上位机改发 `SP_VisionToGimbal_t`
2. 下位机启用 `VisionInit()`
3. 在 `robot_cmd.c` 中用 `Vision_Recv_s`
4. 保留 `auto_gimbal.c` 作为“视觉目标 -> 云台目标”的中间层

---

## 6. 兼容方案：保留旧 `USART1 12字节 float x/y/distance`

如果当前上位机短期不能改协议，可以走兼容方案。

但兼容方案不要再沿用旧工程的写法把数据直接塞进 `gimbal_behaviour.c`。应该把兼容逻辑也放进输入层。

### 6.1 兼容方案应该写到哪里

推荐有两种写法：

#### 写法 A：在 `modules/master_machine` 增加一个 legacy backend

例如新增一个兼容宏：

```c
#define VISION_USE_LEGACY_UART
```

在 `master_process.c` 中新增一组兼容实现：

- `VisionInit(&huart1)`
- 解析 12 字节结构
- 填充到 `Vision_Recv_s`

#### 写法 B：单独新建一个 legacy 模块

例如：

- `modules/legacy_pc_vision/legacy_pc_vision.c`
- `modules/legacy_pc_vision/legacy_pc_vision.h`

该模块只做：

1. 收 `USART1`
2. 解出 `x/y/distance`
3. 输出统一结构给 `robot_cmd`

如果后面还有继续维护打算，优先写法 A。

### 6.2 兼容方案不能直接复用 `AutoGimbalRun()`

这是迁移时最容易犯错的地方。

原因是两边语义不同：

- `Basic_Third_Hero/auto_gimbal.c` 期望收到的是“绝对 yaw/pitch 目标角（rad）”
- 旧工程 `AutoGimbal.c + gimbal_AUTO_angle_control()` 实际使用的是“图像误差/偏差量”，然后乘灵敏度直接累加到控制量

也就是说：

- 新框架：`视觉给绝对目标`
- 旧工程：`视觉给增量偏差`

因此，如果你保留旧上位机协议：

### 6.3 正确写法

在 `robot_cmd.c` 中新增一个“兼容旧视觉偏差”的分支：

```c
gimbal_cmd_send.yaw += legacy_vis->x * yaw_k;
gimbal_cmd_send.pitch += legacy_vis->y * pitch_k;
```

而不是把 `legacy_vis->x/y` 直接喂给 `AutoGimbalRun()`。

### 6.4 建议的数据结构

兼容结构可以定义为：

```c
typedef struct __attribute__((packed))
{
    float x;
    float y;
    float distance;
} LegacyVisionRecv_s;
```

并通过 `USARTRegister()` 接入 `huart1`。

### 6.5 兼容方案的一个硬限制

如果你继续保留旧工程那种：

- `USART1 RX` 收自瞄
- `USART1 TX` 发 `0xA6 + SBUS`

那么你必须确认上位机现在仍然依赖“主控转发的遥控原始帧”。

如果上位机不依赖，就应该彻底删除这个功能。

如果上位机依赖，也不要把该数据和 `master_process` 的视觉协议共用一条协议流。否则会出现：

1. 上位机收到了两种不同格式的数据
2. 下位机也无法知道当前 TX 的格式边界
3. 后期扩展一定出问题

因此兼容方案的原则是：

- `USART1` 只保留一种协议
- 不要一边发 `SP`/`legacy vision`，一边再发 `0xA6 + sbus`

## 7. 旧工程逻辑迁入 `Basic_Third_Hero` 的具体落点

## 7.1 遥控器摇杆/键鼠映射

旧工程这些逻辑应迁入：

- `application/cmd/robot_cmd.c`

不要再写入：

- `application/gimbal/gimbal.c`
- `application/shoot/shoot.c`
- `application/gimbal/auto_gimbal.c`

原则：

- `cmd` 决定模式
- `gimbal/shoot` 只执行

## 7.2 视觉接管云台

如果是推荐方案：

- 视觉接收写在 `modules/master_machine/master_process.c`
- 控制仲裁写在 `application/cmd/robot_cmd.c`
- 目标求解写在 `application/auto_gimbal.c`

如果是兼容方案：

- 兼容协议写在 `modules/master_machine` 或新 legacy module
- 偏差转角度增量的逻辑仍写在 `robot_cmd.c`

## 7.3 云台执行层

`gimbal` 应继续只接受：

- `Gimbal_Ctrl_Cmd_s`

而不应该自己持有：

- 遥控器句柄
- 上位机句柄

否则会重新退回旧工程那种“执行模块直接读输入”的耦合方式。

## 7.4 射击逻辑

旧工程中：

- 鼠标左键
- 拨杆上下
- `Q/E`

这些射击控制条件应统一迁入：

- `robot_cmd.c`

然后通过：

- `Shoot_Ctrl_Cmd_s`

发给 `shoot`。

## 7.5 舵机/弹舱盖

旧工程中舵机逻辑读了：

- `rc.ch[4]`
- `mouse.press_r`

在新框架中应先转换成：

- `lid_mode`
- 或单独的 `servo_cmd`

不要在执行层再次直接读取遥控器。

## 8. 推荐的最小改动顺序

如果目标是“先让它跑起来，再逐步清理”，建议按下面顺序做。

### 第一步：先把遥控器链路接好

确认：

1. `RemoteControlInit(&huart3)` 正常工作
2. `robot_cmd.c` 中能稳定读取 `rc_data`
3. 模式切换全部收口到 `RemoteControlSet()/MouseKeySet()`

### 第二步：决定电脑链路走哪种协议

二选一：

1. 改上位机，走 `master_process` 的 `SP` 协议
2. 不改上位机，新增 legacy UART 兼容层

### 第三步：打开视觉初始化

在 `RobotCMDInit()` 中启用：

```c
vision_recv_data = VisionInit(NULL);      // VCP
vision_recv_data = VisionInit(&huart1);   // UART
```

### 第四步：在 `robot_cmd.c` 做控制仲裁

要明确三件事：

1. 当前是遥控器模式、键鼠模式还是视觉模式
2. 当前是否允许视觉覆盖 yaw/pitch
3. 当视觉离线时是否回退手动控制

### 第五步：只让 `gimbal` 接收结果，不再接触输入源

此时 `gimbal` 只看：

- `Gimbal_Ctrl_Cmd_s`

`shoot` 只看：

- `Shoot_Ctrl_Cmd_s`

## 9. 我给你的明确建议

### 建议 1

不要把旧工程的 `application/remote_control.c`、`MDK-ARM/AutoGimbal.c`、`gimbal_behaviour.c` 原样搬进 `Basic_Third_Hero`。

原因：

- 旧工程是“任务里直读输入”
- 新框架是“输入统一收口到 cmd”

直接搬会破坏框架边界。

### 建议 2

电脑链路优先改成 `master_process` 的 `SP` 协议，不要继续使用旧 `12字节裸 float`。

原因：

- 当前 `Basic_Third_Hero` 已经有完整通信栈
- 已经支持 `VCP/UART/CAN`
- 已经支持在线判断和 CRC

### 建议 3

如果短期必须兼容旧上位机，那就兼容在“输入层”，不要兼容在“云台层”。

也就是：

- 可以新增 legacy `VisionInit`
- 但不要让 `gimbal.c` 直接去读 legacy buffer

### 建议 4

不要在 `USART1` 上继续混发旧 `0xA6 + sbus` 数据，除非上位机确实强依赖它。

如果确实依赖，也建议：

1. 另开端口
2. 或改为标准化遥测协议

不要和视觉控制共享一条无边界串口流。

---

## 10. 最终迁移结论

把旧工程迁入 `Basic_Third_Hero/gimbal` 时，正确的思路不是：

- 把旧任务一个个搬过来

而应该是：

1. 遥控器输入复用 `modules/remote`
2. 电脑输入复用 `modules/master_machine`
3. 所有输入统一汇总到 `application/cmd/robot_cmd.c`
4. `application/auto_gimbal.c` 只负责视觉目标求解
5. `gimbal/shoot` 只消费 cmd 发布的结果

如果你要的是长期可维护版本，推荐路线只有一条：

- `USART3` 继续接遥控器
- `USB VCP` 或 `USART1` 仅跑 `master_process`
- 删除旧 `USART1 sbus 转发`
- 让 `robot_cmd` 成为唯一控制收口点

---

## 11. 迁移时的直接修改清单

### 推荐方案

1. 在 `application/robot_def.h` 选择 `VISION_USE_VCP` 或 `VISION_USE_UART`
2. 在 `application/cmd/robot_cmd.c` 打开 `vision_recv_data = VisionInit(...)`
3. 在 `robot_cmd.c` 中保留 `RemoteControlInit(&huart3)`
4. 在 `robot_cmd.c` 中重写旧工程的模式映射和按键逻辑
5. 删除旧工程风格的 `USART1 sbus` 转发思路
6. 用 `Vision_Recv_s` 和 `AutoGimbalRun()` 串起视觉控制

### 兼容方案

1. 新增 legacy `USART1` 接收模块
2. 仅把 `x/y/distance` 兼容成统一输入
3. 在 `robot_cmd.c` 中把 `x/y` 当作增量控制使用
4. 不要直接把旧兼容 buffer 塞进 `gimbal`
5. 不要让 legacy 协议和 `SP` 协议共用一条发送流
